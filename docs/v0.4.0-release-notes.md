# CodeConductor v0.4.0 — Release Notes

**Release date:** 2026-07-10
**Previous version:** v0.3.x

v0.4.0 is the first release that ships a **multi-phase workflow loop** and
the first to ship **stack-specific presets** as first-class artifacts. The
focus is reproducibility: every task that enters the system runs through the
same 8-phase pipeline, the same council consensus rules, and the same
guardrails — and the agents that show up are the ones that actually fit the
stack you are working in.

---

## Highlights

- **Workflow Loop Core** — 8-phase pipeline (`intake → structure → design →
  test → implement → validate → council → compact`) with wall-clock, files
  modified, and lines changed guardrails, plus human STOP gates after Design
  and Council Verdict.
- **Stack-specific presets** — `ts-next-drizzle`, `spring-kotlin-jpa`,
  `laravel-tall`, `python-data-api` each ship tuned `architect` and
  `implementer` contracts plus the matching specialized skills.
- **Council consensus v0.4.0** — per-agent confidence thresholds and a
  `complianceVeto` channel that override majority verdicts the same way the
  security veto already did.
- **Goal orchestration** — `goal "<objective>"` writes a dependency-ordered
  task graph that the orchestrator delegates in topological order; blocked
  dependencies halt their dependents.
- **Memory compression + escalation emitter** — Phase 5 memory index plus
  the new `loop-controller` escalation report keeps inter-agent context
  inside the token budget and surfaces guardrail breaches to the human.
- **9 specialized skills** — bundle coverage for Drizzle schemas, Tailwind
  responsive audits, SEO/GEO analytics, JPA N+1 detection, Spring auth
  audits, Livewire/Alpine bridges, FastAPI Pydantic strict mode, TDD
  mutation testing, and auth token inspection.
- **Parallel subagents** — routing policy v0.4.0 enables safe parallel
  execution for eligible agent sequences (architect + implementer pattern,
  council verdict fan-out).
- **Prompts and contracts v0.4.0** — the bundled contracts under
  `presets/opencode/prompts/v0.4.0/` reflect every change in this release.
  See [prompt-versioning.md](prompt-versioning.md) for the version table.

## Workflow Loop Core (Phase A)

The new `runWorkflowPipeline()` in `src/core/pipeline/workflow-loop.ts`
executes the canonical 8-phase loop:

```text
intake → structure → design → test(RED) → implement(GREEN) → validate → council → compact
```

### Phases

| #  | Phase        | Purpose                                                       | STOP gate |
| -- | ------------ | ------------------------------------------------------------- | --------- |
| 1  | `intake`     | Parse raw request into a Task Card                            | —         |
| 2  | `structure`  | Compact the Task Card to scope and constraints                | —         |
| 3  | `design`     | Produce a Technical Plan with `filesAffected` + edge cases     | **yes**   |
| 4  | `test`       | Write failing tests (TDD red) — suite MUST fail               | —         |
| 5  | `implement`  | Make tests pass (TDD green), max 3 iterations                 | —         |
| 6  | `validate`   | Mutation testing (≥ 80% score) + diff scope audit              | —         |
| 7  | `council`    | `councilConsensus()` over reviewer verdicts                   | **yes**   |
| 8  | `compact`    | Persist summary to the memory index                           | —         |

### Operational guardrails

`PipelineConfig` accepts three numeric guardrails. Any breach short-circuits
the pipeline with a structured error:

| Guardrail             | Config key           | Default | Trigger                                  |
| --------------------- | -------------------- | ------- | ---------------------------------------- |
| Wall-clock timeout    | `maxWallClockSeconds`| `0` off | Pipeline elapsed time exceeds the limit  |
| Files modified        | `maxFilesModified`   | `0` off | `git status --porcelain` count > limit   |
| Lines changed         | `maxLinesChanged`    | `0` off | `git diff --numstat` total > limit       |

Guardrails are checked between phases, not inside the agent callback, so a
running implementation cannot bypass them.

### STOP gates

Two phases require explicit human approval via the `onStopGate` callback:

- After **Design** (phase 3) — confirms the plan before any code is written.
- After **Council** (phase 7) — confirms the verdict before it is persisted.

`onStopGate` returns `'APPROVE'`, `'REJECT'`, or `'ESCALATE'`. Anything other
than `'APPROVE'` aborts the pipeline with the reason attached to the result.

### Minimal example

```ts
import { runWorkflowPipeline } from './src/core/pipeline/workflow-loop';

const result = await runWorkflowPipeline('Add password reset endpoint', {
  maxWallClockSeconds: 600,
  maxFilesModified: 25,
  maxLinesChanged: 800,
  callbacks: {
    runIntake: async (raw) => /* ... */,
    runStructure: async (card) => /* ... */,
    runDesign: async (card) => /* ... */,
    runTest: async (plan) => /* ... */,
    runImplement: async (plan, feedback) => /* ... */,
    runValidate: async (plan) => /* ... */,
    runCouncilReview: async (plan, validation) => /* ... */,
    runCompact: async (card, summary) => /* ... */,
    onStopGate: async (phase, data) => 'APPROVE',
  },
});
```

See `src/core/pipeline/workflow-loop.ts` and `test/pipeline.test.ts` for the
contract surface and the full test matrix.

## Stack-specific presets

Four presets now ship as first-class artifacts in `presets/`. Each one
bundles an `architect.md` and an `implementer.md` tuned to a single stack,
plus the matching specialized skills (see below). They are registered in
`src/core/presets/preset-registry.ts`.

| Preset              | Stack                                                      | Best for                                                |
| ------------------- | ---------------------------------------------------------- | ------------------------------------------------------- |
| `ts-next-drizzle`   | Next.js / Astro, Tailwind, Drizzle ORM, Bun, Postgres      | Modern web apps on the JS/TS data-fetching stack        |
| `spring-kotlin-jpa` | Spring Boot, Kotlin/Java, Gradle, JPA, Hibernate           | Backend services with JPA, Hibernate, or Spring Security|
| `laravel-tall`      | Laravel, Blade, Livewire, Alpine.js                        | TALL-stack apps with reactive Livewire components       |
| `python-data-api`   | Python, FastAPI, Django, uv                                | Async APIs and data pipelines                           |

### Install

`init` / `detect` identifies the stack from the project and wires the
matching specialized skills automatically when you run `install preset`.
The full set of assets for a stack-specific preset is in
`presets/<preset-name>/agents/` — copy them manually if you need to apply a
preset by name:

```bash
# Auto-detect: skills for the detected stack are installed
npx cc-codeconductor install preset --target opencode

# Manual: copy the preset's architect + implementer contracts directly
cp presets/ts-next-drizzle/agents/*.md .opencode/agents/
```

Files are written to the target runner's `agents/` directory. With
`--locale=es` the contracts are rendered in Spanish.

### Registry

The full list of presets is exposed programmatically:

```ts
import { listPresets, getPreset } from './src/core/presets/preset-registry';

listPresets();
// [
//   { name: 'council',            version: '0.1.0', ... },
//   { name: 'seo-hotel',          version: '0.3.0', ... },
//   { name: 'ts-next-drizzle',    version: '0.4.0', ... },
//   { name: 'spring-kotlin-jpa',  version: '0.4.0', ... },
//   { name: 'laravel-tall',       version: '0.4.0', ... },
//   { name: 'python-data-api',    version: '0.4.0', ... },
// ]
```

See `src/core/presets/preset-registry.ts` and
`src/core/presets/preset-resolver.ts`.

## Council consensus v0.4.0

`src/domain/council/council-consensus.ts` now enforces two new rules on top
of the existing majority/unanimous algorithms and security veto.

### Compliance veto

`CouncilVerdictInput` gains an optional `complianceVeto: boolean`. When
`true` and the verdict is `REJECTED`, the council verdict becomes
`REJECTED` regardless of majority — same precedence as the security veto.

```ts
const verdict = councilConsensus([
  { agentId: 'a1', agentRole: 'security',    status: 'APPROVED', securityVeto: false, complianceVeto: false, findings: [], summary: 'ok' },
  { agentId: 'a2', agentRole: 'compliance',  status: 'REJECTED', securityVeto: false, complianceVeto: true,  findings: [], summary: 'policy breach' },
  { agentId: 'a3', agentRole: 'architect',   status: 'APPROVED', securityVeto: false, complianceVeto: false, findings: [], summary: 'ok' },
]);

verdict.status === 'REJECTED';                // true
verdict.complianceVetoApplied === true;       // true
verdict.vetoByAgentId === 'a2';               // true
```

### Confidence thresholds

Each `CouncilVerdictInput` accepts an optional `confidence: number` in
`[0, 1]`. The consensus engine computes `averageConfidence` and flags
`hasLowConfidence` and applies the following rules **before** the majority
check:

- If any agent's `confidence < 0.6` → status = `ESCALATED`
- If `averageConfidence < 0.7` → status = `ESCALATED`

Both rules can be disabled by passing `0` / `1` literally, but the
recommended pattern is to surface them as `ESCALATED` so the human reviews
the borderline verdict.

### Backwards compatibility

Defaults match v0.3.x exactly. Existing callers that omit `confidence` and
`complianceVeto` see no behavior change. New behavior is opt-in by adding
those fields to the verdict input.

## Goal orchestration

`npx cc-codeconductor goal "<objective>"` (alias: `cc-goal`) now feeds the
orchestrator's dependency-aware delegation loop.

### Planner

`src/core/goal/goal-planner.ts` matches the objective against built-in
templates (auth, crud, search, notification, migration) and falls back to a
generic 4-task chain: `task-coach → architect → implementer → tester`.

### State

`src/core/goal/goal-state.ts` writes `.codeconductor/current-goal.yml`:

```yaml
objective: Add user authentication
tasks:
  - id: task-1
    title: Define task card and scope
    agent: task-coach
    status: pending
  - id: task-2
    title: Design authentication flow
    agent: architect
    depends_on: [task-1]
    status: pending
  - id: task-3
    title: Implement authentication
    agent: implementer
    depends_on: [task-2]
    status: pending
  - id: task-4
    title: Test authentication
    agent: tester
    depends_on: [task-3]
    status: pending
```

### Orchestrator delegation

The orchestrator reads the file and delegates tasks in dependency order. A
task is only routed after all its `depends_on` targets complete with status
`done`. If a dependency is `blocked`, the dependent task stays `pending`
until the blocker is resolved.

```bash
npx cc-codeconductor goal "Add user authentication"
npx cc-codeconductor goal "Implement CRUD for invoices" --output json
npx cc-codeconductor cc-goal "Add search with filters"
```

## Memory compression + escalation emitter

### Memory compression

`src/core/memory/memory-index.ts` provides a Phase-5 memory index that
keeps inter-agent context within the configured token budget. Old entries
are compacted to a summary before they fall out of the active window, so
the next phase of the loop can still see what previous phases decided.

The hook is registered in `src/core/compaction/compaction-hook.ts` and is
invoked from the loop controller between phases.

### Escalation emitter

`src/core/loop/escalation-emitter.ts` collects `CompileError[]` history,
attempted fixes, and the original context, then formats an
`EscalationReport` when the loop hits a guardrail or exhausts the iteration
budget. The report is the artifact the human reviews before resuming or
rejecting the loop.

```ts
import { escalationEmitter, runCompileFixLoop } from './src/core/loop/loop-controller';

const { success, escalationReport } = await runCompileFixLoop({ /* ... */ });
if (!success) {
  await escalationEmitter(report, { notify: 'human' });
}
```

## Parallel subagents

Routing policy v0.4.0 enables safe parallel execution for eligible agent
sequences. The new policy lives in `docs/routing-policy.md`.

| Route                                    | Concurrency      |
| ---------------------------------------- | ---------------- |
| `architect` + `implementer` (design + impl)| sequential      |
| Council verdict fan-out                  | parallel         |
| `complexity-auditor` + `reviewer`        | parallel         |
| `tester` while `implementer` runs        | parallel         |

Parallel subagents are wired through the `runner` core module — see
`src/core/runner/`.

## Migration guide

1. **Run `init --force`** in any project that is currently on v0.3.x. The
   command will refresh `.codeconductor/config.yml` and re-copy the council
   + policy presets.
2. **Pick a stack preset** (optional) — if the project matches one of the
   four supported stacks, copy the matching preset's contracts into the
   target runner manually:
   ```bash
   cp presets/ts-next-drizzle/agents/*.md .opencode/agents/
   ```
   `init` / `detect` already wires the matching specialized skills into the
   generic preset automatically.
3. **Re-run `doctor`** to confirm the contracts and the runner directories
   are aligned with v0.4.0.
4. **Wire the workflow loop** (optional) — if you have a custom orchestrator,
   import `runWorkflowPipeline` from
   `src/core/pipeline/workflow-loop.ts` and pass your existing agent
   callbacks. Existing ad-hoc loops continue to work.
